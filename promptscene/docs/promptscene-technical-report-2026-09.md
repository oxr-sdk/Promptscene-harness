## 1. 요약

### 1.1 한 줄 정의

**검증된 멀티유저 XR 룸 플랫폼 위에서, 자연어로 콘텐츠 모듈을 선택·조합·배선하고, 그 결과가 실제로
성립하는지를 라이브 Unity 에디터에서 기계로 판정하는 시스템**이다.

산출물은 두 갈래다.

1. **런타임 코드** — 얇은 코어(`PromptScene.Core`)와 그 위에 옵트인으로 얹히는 콘텐츠 모듈. 두 Unity
   프로젝트(XRCollabDemo, XumFlow:studio)에서 각각 성립을 실증했다.
2. **자동화 표면** — 그 조립·검증 절차를 동결한 Claude Code 플러그인 `promptscene-harness`. 스킬 5종.

### 1.2 핵심 결과 (전부 라이브 판정)

| # | 결과 | 근거 |
|---|---|---|
| R1 | **3층 아키텍처(SYSTEMS / FEATURES / COMPOSITIONS)가 두 개의 서로 다른 Unity 프로젝트에서 성립.** 계약 인터페이스 무수정, FEATURE↔FEATURE 참조 0 유지 | §7.2, §7.4 |
| R2 | **자연어 한 줄 → 3기능 룸 합성 + 구조 자동판정 PASS.** 요청과 무관한 기능을 실제로 **탈락**시킨 음성 증거 포함 | §7.3 (M4) |
| R3 | **서버 권위 게임 루프(COMPOSITIONS 층)를 전제 파괴 없이 증축.** 계약 추가는 인프로세스 이벤트 버스 1개, `IRoomCore` 무변경 | §7.3 (D2) |

### 1.3 이 프로젝트가 하지 않는다고 명시한 것

보고서 전체에서 반복되는 **정직 계약(honesty contract)** 이 있다. 하네스가 증명하는 것은
**구조·계약 적합성과 관측된 런타임 신호**뿐이며, 다음은 **증명하지 않는다**: 재미·밸런스·미감, 실기기
손맛, 3인 이상 동시 접속, 배포 파이프라인, 실제 키보드/마우스 2인 조작. 각 실증 절은 자기 범위의
"밖"을 명시적으로 열거한다(§5.5).

## 2. 배경과 문제 정의

### 2.1 출발점

멀티유저 XR 협업 앱(XRCollabDemo)에서 **"이런 룸 만들어줘"** 라는 자연어 요청을 씬으로 바꾸려 할 때,
실제 비용은 창의적인 부분에 있지 않았다. 비용은 **틀리면 전부 죽는 배선**에 있었다.

- 네트워크 매니저·스포너·프리팹 컬렉션의 일치
- FishNet 씬 오브젝트의 SceneId 직렬화
- 로비→룸 씬 전환 설정
- 전용 서버 실행 파일의 재빌드 타이밍
- 아바타 스폰 경로

이 중 하나만 어긋나면 증상은 **조용하다**. 룸에 들어가지고, 로비도 사라지고, 로그에는 "become a
player"까지 찍히는데 **아바타만 안 뜬다**(§8.1). 사람이 하루를 태우는 지점은 여기였다.

### 2.2 문제 정의

따라서 문제를 이렇게 좁혔다.

> **자연어→씬 자동화의 가치는 창의적인 20%가 아니라, 틀리면 다 죽는 80%를 기계로 보장하는 데 있다.**
> 사람의 반복 예산은 손맛·미감 판단에 남겨야 한다.

이 결정은 [design-directions-2026-07.md](../promptscene/docs/design-directions-2026-07.md) **D1**에
기록되어 있고, 이후 모든 설계·검증 판단의 기준선이 된다.

### 2.3 왜 기존 방식으로 안 되었나

- **레퍼런스 앱 이식 불가.** 기능 레퍼런스 소스(DeepChairProject)는 앱 레이어가 XRCollabDemo에 없어
  lift-and-shift가 성립하지 않는다 → 계약 위에 **클린 재구현**이 정석이라는 판정([HANDOFF §2](../HANDOFF.md)).
- **문서만으로는 부족.** 플랫폼 SDK의 공식 예제 코드에서 문법 오류가 실제로 확인되었다(§6.3). 그래서
  "문서는 지도, 소스는 진실"을 라우팅 규약의 대원칙 1로 못박았다.
- **구조 검증의 부재.** "돌아간다"를 사람 눈으로만 판정하면 회귀를 잡을 수 없다. 기계가 읽을 수 있는
  **신호(signal)** 정의가 필요했다.

## 3. 목표와 사거리 — "정직한 주장"의 정의

### 3.1 사거리 재정의 (D1)

| | 내용 |
|---|---|
| **주장한다** | 검증된 룸 플랫폼 위에서, 자연어로 모듈을 선택·조합·파라미터화하고 **구조를 자동 검증**한다 |
| **주장하지 않는다** | 자연어로 임의의 게임을 합성한다 |
| **사거리 안** | 기능들이 **직교**하는 구성(측정 + 채팅 + 잡기가 있는 협업 룸) |
| **사거리 밖** | 기능이 깊게 결합된 게임 루프 — D2(COMPOSITIONS 층)로 확장 가능하나 D4-2(예측)의 한계는 남음 |

근거는 자연어→씬이 본질적으로 **명세 부족 문제**라는 것이다. "축구" 한 단어 뒤에 수백 개의 미결정이
있고, 그 결정을 대화로 좁히는 층(D6 상담층)이 없으면 시스템은 사용자에게 지킬 수 없는 약속을 한다.

### 3.2 정직 계약 (honesty contract)

프로젝트 전체를 관통하는 규율이며, 문서마다 자기 절 끝에 반복 기입한다.

1. **증명된 것과 시연한 것을 구분한다.** M4 세션에서 2클라 데모(채팅/측정/핸드오버)는 명시적으로
   **"시연이지 하네스 증명이 아니다"** 라고 기록했다.
2. **밖을 열거한다.** 각 실증 절은 자기가 증명하지 **않은** 것을 표로 남긴다.
3. **신호로 말한다.** "잘 된다"가 아니라 "①~④ 신호 PASS"로 말한다.
4. **음성 증거를 남긴다.** 카탈로그 매칭이 실제로 변별한다는 증거로, 선택되지 **않은** 기능을
   `notSelected`에 박제한다(§7.3 M4).

### 3.3 상담층 설계 원칙 (D6)

이후 확장 방향으로 **상담층 = 견적 + 브리프**를 정의했다. 핵심 규율은 하나다.

> **지킬 수 있는 것만 질문한다.** 브리프 질문은 능력 지도의 ✅·⚠ 항목에서만 파생하고, ⛔ 항목은
> 질문 대신 **의향 기록 + 개척 청구서**로 남긴다.

즉 능력의 경계가 곧 질문의 경계가 되어, 상담이 정직 계약의 사용자 대면 표현이 된다. 이 원칙은 이후
`/add-component`의 Phase 0 상담과 옵션 게이트로 구현된다(§6.1).

## 4. 시스템 아키텍처

정본: [promptscene-content-contract.md](../promptscene/docs/promptscene-content-contract.md) (규격 SSOT),
[ARCHITECTURE.md](../promptscene/docs/ARCHITECTURE.md) (설계 개념).

### 4.1 3층 모델

```
COMPOSITIONS (게임모드/시나리오)  ← 기능들을 "아는" 유일한 층
      ↓ 한 방향
FEATURES (Ruler, Chat, Target…)   ← 여전히 서로 모름 (이벤트 버스로만 만남)
      ↓ 한 방향
SYSTEMS (네트워크·세션·스폰·코어)  ← 여전히 아무것도 모름
```

| 층 | 정의 | 업계 대응 | 판별 테스트 |
|---|---|---|---|
| **SYSTEMS** | 룸이 *작동하는 방식* 그 자체. 네트워크·세션·입장·스폰·코어 레지스트리 | Core / Systems | "빼면 프로젝트가 깨지나?" → 깨진다 |
| **FEATURES** | 토대 위에 얹는 선택 모듈. 기능·환경 연출 포함 | UE5 Game Features / Plugins | 빼도 안 깨진다 |
| **COMPOSITIONS** | 직교하는 FEATURE 여럿을 하나의 루프로 엮는 조율자 | UE5 GameMode / Mediator | 서로 다른 FEATURE 여럿을 조율한다 |

**성립 근거는 의존성 역전이다.** 코어가 기능을 호출하는 것이 아니라, 각 기능이 런타임에 코어의
레지스트리에 **스스로 등록**한다. 그래서 의존은 `COMPOSITIONS → FEATURES → SYSTEMS` **한 방향
비순환**뿐이고, 층을 얹어도 기존 검증 논리(모듈 on/off, 프로젝트 간 이식)가 그대로 산다.

**핵심 귀결:** 자연어 입력이 바뀌어도 **토대는 바뀌지 않는다.** 그래서 토대는 검증된 절차로 얼려
스킬화하고, 변하는 층만 조립하면 자연어→씬 자동화가 성립한다.

### 4.2 계약 인터페이스 (C# v0.2)

네임스페이스 `PromptScene.Core`. FEATURE 모듈은 **이 계약에만** 의존한다.

```csharp
public interface IRoomUserState { string MultiScaleName { get; } }
public interface IInteraction     { void AddClick(Action<RaycastHit> onClick); void RemoveClick(Action<RaycastHit> onClick); }
public interface INetSpawn        { bool IsNetworked { get; } GameObject Spawn(GameObject prefab, Vector3 p, Quaternion r); void Despawn(GameObject instance); }
public interface INetDespawnRequest { void RequestServerDespawn(); }

public interface IEventBus        // COMPOSITIONS 층 활성화용 유일한 계약 추가 (2026-07-21)
{
    void Publish<T>(T evt);                 // 동기 전달. 예외 던지는 핸들러는 로그+격리
    void Subscribe<T>(Action<T> handler);   // (T,handler)당 멱등
    void Unsubscribe<T>(Action<T> handler); // 미구독 핸들러에도 안전
}

public interface IRoomCore
{
    RoomContentRegistry Contents { get; }
    bool TryGet<T>(out T service) where T : class;   // 없으면 false → 호출측이 우아하게 대응
}

public interface IRoomContent       { string Id { get; } void OnRegister(IRoomCore core); void OnUnregister(); }
public interface IToggleableContent : IRoomContent { ContentMeta Meta { get; } bool IsEnabled { get; } void SetEnabled(bool on); }
public interface IScaleScopedContent { void DespawnByScale(string multiScaleName); }
```

**v0.2의 설계 결정 — 제네릭 리졸버.** 서비스를 `IRoomCore`의 명시 프로퍼티로 열거하지 않고
`TryGet<T>`로 조회하게 바꿨다. 그 덕에 **서비스가 늘어도 `IRoomCore`는 안 바뀐다.** 실제로 D2에서
`IEventBus`를 추가할 때 **인터페이스 무변경**으로 통과했다 — 내장 서비스로 등록하고 조회만 추가했다.
코어가 god 인터페이스로 자라는 것을 구조적으로 막는 장치다.

**우아한 실패(graceful failure).** FEATURE는 `OnRegister`에서 필요한 서비스를 `TryGet`으로 확보하되,
실패 시 경고를 남기고 **비활성 상태를 유지**한다. 예외·NullReference를 던지지 않는다. 이것이 템플릿의
표준 동작이며 §5 검증 신호 중 하나(`SetEnabled` 무예외)와 직접 연결된다.

**서비스 4종** (`RoomCore.Awake`에서 등록): `IInteraction`(SimpleClickProvider) ·
`INetSpawn`(FishNetSpawn) · `IRoomUserState` · `IEventBus`(인프로세스 EventBus).

**생명주기 순서 규약.** 서비스 등록 = `Awake`, 콘텐츠 자기등록 = `Start`. Script Execution Order 설정에
의존하지 않고 단계 분리로만 레이스를 막는다 — 콘텐츠가 `TryGet`하는 시점에 서비스가 반드시 존재한다.

### 4.3 씬 계층 규약 (5층)

```
<Room>.unity
├── ===== SYSTEMS =====        ← Core. 항상 존재. 하네스가 존재/와이어 검증
│   ├── Network                (룸서버/클라/마스터 연결)
│   ├── Player                 --PLAYER_SPAWNER (XumPlayerSpawner + Catalog + SpawnTable)
│   └── RoomCore               IRoomCore 구현 + RoomContentRegistry — 특정 기능을 모름
├── ===== ENVIRONMENT =====    Floor, Walls, Lighting, Main Camera
├── ===== UI =====             룸 HUD
├── ===== FEATURES =====       ← 각 모듈이 스스로 등록. 서로 참조 0
├── ===== COMPOSITIONS =====   ← 기능들을 아는 유일한 층
└── ===== _DYNAMIC =====       런타임 생성물
```

**⭐ 골격 예약 규칙 (2026-07-24 확정).** 다섯 층은 **골격이 모두 빈 폴더로 예약**하고, 층의 **내용**은
수요가 있을 때 채운다. 즉 `/assemble-room`은 항상 5층 헤더를 만들고 FEATURES·COMPOSITIONS는 **비워
두며**, `/add-component`가 그 층을 채운다.

이 규칙은 "수요 없는 추상화 금지"(런치패드 회고의 교훈, §9.1)와 충돌하지 않는다. 그 교훈의 실제
위험은 *아직 안 겪은 기능의 인터페이스를 추측해 만드는 것*이지 *빈 폴더의 유무*가 아니기 때문이다.
빈 폴더는 코드도 계약도 만들지 않으므로 추측이 없다.

**studio 편차(실측).** 배포 모델이 다른 프로젝트에서는 `Network` 하위 폴더가 없고(네트워크 매니저가
부트 씬에 있어 전역 접근), `_DYNAMIC`은 런타임 생성물 전용이라 정적 골격에 나타나지 않는다. 나머지
4층은 동일하게 성립한다.

### 4.4 SYSTEMS 불변식 C1~C4

| # | 계약 | 검증 방법 |
|---|---|---|
| C1 | 프리팹 컬렉션 일치 | 룸서버 NetworkManager `_spawnablePrefabs` == 클라 (= DefaultPrefabObjects) |
| C2 | 플레이어 스폰 = XumPlayerSpawner | `--PLAYER_SPAWNER`에 스포너 + Catalog(Desktop/UnityXR) + SpawnTable. FishNet 기본 PlayerSpawner 금지 |
| C3 | 씬 전환 | `_onlineScene=<Room경로>`, **`_offlineScene=Client.unity`** (비면 로비 UI가 안 사라짐) |
| C4 | 실행 토폴로지 | 서버 = Master + Room exe / 에디터 = Client + Room 동시 로드 |

### 4.5 코어 승격 규칙 — 게이트

`IRoomCore`가 god 인터페이스로 자라지 않도록 하는 **명문화된 관문**이며, 하네스의 "SYSTEMS diff 0"
체크에 대한 **공식 예외 절차**다.

1. **mechanism-not-policy 테스트.** 코어에 올라올 수 있는 것은 **메커니즘**(전달·조회·통지의 *방법*)
   뿐이다. **정책**(게임 규칙·승리 조건·밸런스 = "*무엇을* 하나")은 영원히 FEATURE에 남는다.
2. **두 소비자 규칙(rule of two).** 어떤 서비스의 승격은 **두 번째** 기능이 그것을 필요로 할 때
   수행한다. 첫 소비자 단계에서는 FEATURE 내부에 지역적으로 둔다(성급한 일반화 방지).

이 두 규칙은 장식이 아니라 **실제로 승격을 세 번 막았다**(§9.2~§9.4).

## 5. 검증 방법론 — 하네스

### 5.1 "하네스"의 실체

하네스는 독립 실행 코드가 **아니다.** **규격(계약 §5) + 실행 절차(스킬)** 로 존재한다. 즉 판정 기준은
문서에 얼려 두고, 그 기준을 라이브 에디터에서 집행하는 것이 스킬이다.

### 5.2 검증 신호 정의

하네스가 판정하는 신호는 두 묶음이다.

**§6.5 — SYSTEMS 신호 (토대가 안 깨졌나)**

| 신호 | 판정 내용 |
|---|---|
| 아바타 스폰 | `Desktop(Clone)`이 스폰되고 `IsOwner=True` |
| 로비 소멸 | 입장 시 Client 씬 언로드(C3 성립) |
| RoomCore 가동 | 서비스 4종 등록 + 레지스트리 상태 |
| 이동 가능 | WASD-ready |

**§5 — FEATURES / COMPOSITIONS 신호 (콘텐츠가 계약대로 사나)**

| 대상 | 신호 |
|---|---|
| FEATURE | ① 런타임 레지스트리 **자기등록** ② `SetEnabled(true/false)` **예외 없음 + 멱등** ③ 토글형이면 **메타 유효** |
| COMPOSITION | 씬 상주 + **레지스트리에 등록되지 않음**(FEATURE가 아니므로) |
| COMPOSITIONS 층 | **FEATURE↔FEATURE 상호 타입 참조 0** — `grep`으로 기계 판정 |
| 전역 | 컴파일 0 에러, 런타임 Error 0 |

특히 마지막 것이 **D2 층이 도입한 §5급 신규 검증 신호**다. 파일럿 두 FEATURE의 소스에 상대 타입
참조가 하나도 없어야 하고, 상호작용은 오직 `IEventBus` + COMPOSITION 조율로만 성립해야 한다. 이게
성립하면 "게임 루프를 얹어도 직교성이 살아 있다"는 기계적 증거가 된다.

### 5.3 판정 채널

판정 **주체**를 명시하는 것이 이 프로젝트의 특징이다.

| 채널 | 대상 | 방식 |
|---|---|---|
| **MCP 리플렉션** | 에디터 A | Unity MCP 서버의 `script-execute`(Roslyn full-code)로 씬·런타임 상태를 리플렉션 read-back |
| **`-logFile`** | 빌드된 클라 B / 클론 에디터 B | 에폭 타임라인 위의 이벤트 로그를 교차 대조 |
| **상태 파일** | 클론 에디터 B | 프로젝트 루트의 `.promptscene-status` **한 줄**을 매초 덮어씀 → 판정 비용 O(1) |
| **명령 파일** | 클론 에디터 B | 루트의 `.promptscene-cmd` 1줄 = 1명령, 소비 후 삭제 |
| **사람 눈** | 미감·조작감 | 하네스가 판정하지 **않는** 것 |

> **최적화 사례.** 초기에는 B의 판정을 전체 로그 파싱으로 했는데 로그가 **13 MB / 175k 줄**까지 커졌다.
> 상태 파일(덮어쓰기 한 줄)로 바꿔 반복 검증 비용을 O(로그 크기)에서 **O(1)** 로 낮췄다.

### 5.4 2클라 하네스의 진화

단일 에디터가 증명할 수 있는 것은 **"한 클라이언트에서의 구조"** 가 전부다. 두 번째 클라이언트는
구조적으로 그 축 밖에 있다. 이 프로젝트는 그 축을 세 세대에 걸쳐 확보했다.

| 세대 | 시기 | B 프로세스 | 판정 골격 |
|---|---|---|---|
| **1세대 (XRCollab)** | 2026-07-14 | 빌드된 데스크톱 `.exe` + arg 게이트 자동조인 하네스(`AutoJoinClient.cs`) | **공유 에폭 + 역할별 안무 + `-logFile` 교차 대조** |
| **1세대 확장** | 07-16 / 07-20 | 동일 | 같은 골격을 **그랩 5신호 / 채팅 4신호**로 재사용 |
| **2세대 (studio)** | 2026-08-19 | **ParrelSync 클론 에디터** + 역할 브리지 | 같은 골격 + 상태 파일 O(1) 판정 |

**같은 판정 골격이 3연속 재사용되었다**(측정 → 그랩 → 채팅)는 사실은 그 자체로 기록해 두었다. N명
하네스를 만들 때 이 골격(에폭 타임라인 · 역할 안무 · 신호 표 판정)을 **판정 코어로 승격**하는 것이
자연스러운 출발점이라는 판단이다.

### 5.5 정직 계약의 기계적 표현

각 검증 절은 다음 3항을 반드시 남긴다.

1. **증명됨** — 판정 주체와 환경을 명시(예: "같은 머신, 에디터 2개, 데스크톱, A=MCP·B=logFile 판정")
2. **밖(미실증)** — 열거
3. **원상복구** — 세션이 건드린 파일의 md5 전후 대조

3번은 특히 엄격하게 집행했다. S2 세션에서는 대상 씬 파일이 **세션 시작 시점부터 이미** git HEAD와
달랐음을 발견하고(이전 세션의 작업 상태), **HEAD로 되돌리지 않고 발견 시점 상태로 복원**했다.

### 5.6 가드 검증의 원칙

> **가드는 *통과* 테스트가 아니라 *차단 재현*으로 검증한다.**

fail-open이면 가드가 조용히 무력화되므로 "안 걸렸다 = 안전"이 아니다. 실제 차단이 재현되는지를
봐야 한다. 같은 원칙을 역할 브리지에도 적용했다 — 원본 에디터에서 훅이 **돌았고 아무것도 하지
않았음**(마커 `applied=False`)까지 확인해서, "안 돌아서 무사한 것"과 구분했다(§7.5).

묻지 않는다**("UI까지", "멀티까지", "구조만"). 이는 D6의 "갈림길만 질문한다" 원칙의 구현이다.

③ 사람이 쓴 스크립트를 **배선·검증만** 대행. 어느 경로든 판정 기준(§5)은 동일하다.

### 6.2 가드레일 훅

**목적:** "패키지 = 토대의 일부 = 읽기 전용" 규칙을 기계적으로 집행한다.

- **차단 대상:** `Library/PackageCache/**`, `Packages/manifest.json`, `Packages/packages-lock.json`
- **구현:** `PreToolUse` 훅(`Write|Edit|MultiEdit|NotebookEdit|Bash` 매처), 종료 코드 2 = 도구 호출 차단
- **회귀 러너:** `test-guard-readonly-paths.sh` 상비

**실제로 잡은 결함 — Windows 백슬래시 fail-open.** 가드 정규식이 슬래시(`/`) 경로만 매칭해서
백슬래시(`\`) 경로가 **무검사 통과**했다. Windows의 파일 편집 도구는 백슬래시 경로를 넘기므로 가드가
조용히 무력화된 상태였다. → 입구에서 `\`→`/` **정규화** + 두 구분자 모두 커버하는 **회귀 러너**로 봉합.

**부수 사실 2건.**
- 가드는 **보수적으로 차단**한다. 명령 문자열에 보호 경로가 들어가면 읽기성 의도라도 막힌다 —
  `manifest.json`을 언급하는 `cp` 백업조차 차단된다.
- 가드는 **서브에이전트 내부 도구 호출에도 fail-closed로 적용**됨을 라이브 검증했다.

### 6.3 문서·소스 라우팅 규약

플랫폼 API를 코드에 쓰기 전에 어디를 읽을지를 정한 규약이다. 대원칙 4개.

1. **문서는 지도, 소스는 진실.** 플랫폼 API는 **반드시 PackageCache 실제 소스에서 시그니처를 확인**한다.
   공식 문서의 예시 코드에 문법 오류가 확인된 바 있어 **문서 코드 복붙을 금지**한다.
2. **원본만 읽는다(SSOT).** 문서 내용을 다른 파일로 요약·복사해 두지 않는다.
3. **PackageCache는 읽기 전용.** 훅이 기계적으로 차단하지만, 우회 시도 자체를 하지 않는다.
4. **원격 private 레포는 인증된 CLI로 지정 경로만.** 익명 접근 금지. 버전 스큐 때문에 원격 문서는
   **지도로만** 쓰고 시그니처의 진실은 로컬 소스에서 재검증한다.

**⭐ 0층 심볼 인덱스 (2026-07-27 도입).** SSOT 원칙의 **유일한 예외**로, 소스에서 **기계 추출한
포인터**(`types.md` / `members.tsv` / `headings.md`)를 둔다. 사람이 쓴 요약이 아니고, 패키지 해시로
**자기 무효화**되며, **주장의 근거로 쓰지 않는다**(찾기 전용)이므로 SSOT를 깨지 않는다.

도입 근거는 실측이다. 기준선 질의를 4계층만으로 풀었을 때 **왕복 6회 / 유입 약 8,000자**였고 그중
**네트워크 왕복 2회가 수확 0**이었다. 같은 질의를 인덱스 grep 1회로 풀면 **답이 더 많이** 나왔다.
병목은 코퍼스 크기가 아니라 **경로 재발견 + grep 추측 + 통짜 읽기**였다는 진단이다.

> 인덱스는 **커밋하지 않는다** — 이 레포는 공개이고 대상 패키지는 private이다(유출 방지).

### 7.3 멀티플레이 실증 시리즈 (M / D / V)

모두 **2클라 라이브 판정**이다.

#### M1 — 결과값 공유 (2026-07-14~15)

- 에디터 클라 + 빌드된 데스크톱 클라 2인을 localhost로 접속
- ① 자기 아바타 소유권 ② 원격 아바타 ③ 위치 전파를 **양측 시점**에서 판정
- Ruler 측정값의 **생성·제거 양방향 전파** 확인
- 계약 `INetSpawn`을 `LocalNetSpawn` → **`FishNetSpawn`** 으로 실체화(§4.5 메커니즘 승격)
- 사람이 직접 몰아볼 수 있는 인게임 최소 HUD(`RulerHudUI`, IMGUI) 추가·검증

> **narrowness 기록.** `Spawn(prefab,pos,rot)`은 per-object 데이터를 못 나른다(클라는 ServerRpc 왕복 후
> null을 반환하므로 초기화 핸들도 없다). 그래서 결과값은 **FEATURE 프리팹 내부 NetworkBehaviour**가
> 나른다. 계약 §1이 "모듈 내부는 자유"라고 명시하므로 그 컴포넌트는 플랫폼 API를 직접 써도 되고,
> 등록되는 `IToggleableContent`는 여전히 `PromptScene.Core`만 참조한다. **경계가 지켜지는 방식**의 실례다.

#### M2 — 잡기 기반 소유권 (2026-07-16, D4-1)

**5신호 전부 PASS.** ① A잡기 Owner=A ② A놓기 후 위치 전파 + Owner 유지(비반납) ③ B탈취 Owner=B
④ B놓기 위치 전파 ⑤ A재탈취 Owner=A (양측 교차 일치).

**SYSTEMS/계약 무수정.** 사전 조사에서 SDK가 이미 소유권 기계(Takeover + ServerRpc)를 제공하고
client-auth `NetworkTransform`이 소유권 이전 시 authority를 승계함을 확인했다. 접점은 `RequestOwnership()`
**한 줄**이라 FEATURE 지역 감싸기로 충분했다 — 계약 승격은 두 번째 소비자 시점으로 미뤘다(§9.3).

#### M3 — 채팅 양방향 (2026-07-20)

**4신호 PASS.** ① A 발신 5건 → B 수신(내용 + 발신자 일치) ② B 회신 2건 → A 수신 ③ 연속 5건 **순서
보존** ④ 발신자 표시 양측 교차 일치.

- **신규 플랫폼 API 0.** 검증된 두 기계의 조합만 사용 — `ServerRpc(RequireOwnership=false)` 상행(M2 동형)
  + `ObserversRpc` 하행(M1 동형)
- **발신자는 서버가 주입한 ClientId** (위조 불가). 닉네임 시스템을 발명하지 않았다
- 신규 설계 지점 1개: **채널 스폰-또는-재사용** — 2클라가 각자 스폰해 채널이 2개가 되는 것을 방지.
  재시도 루프가 조인 flakiness를 흡수하고, 동시 인에이블 레이스는 수신 전 채널 집계로 무해화
- **v1 정직 한계:** 백필 없음(늦게 조인하면 과거 메시지를 못 본다). 패널에 명시
- **Core 메커니즘 일반화 1건(정직 기록):** 월드 클릭 억제 플래그를 단일 bool → **클레임 기반**으로 교체.
  패널이 2개가 되면 마지막-쓰기-승리로 억제가 조용히 깨지는 잠재 버그의 수정이며, SYSTEMS 파일 1개 수정이나
  메커니즘-비정책 테스트를 통과한다(계약 무수정)

#### M4 — 다기능 합성 피날레 (2026-07-20)

자연어 한 줄을 **슬래시 표면으로 발동**했다: *"채팅으로 다른 참가자와 소통하고, 측정한 내용을 서로 볼

### 7.4 2차 트랙 (XumFlow studio) 이식 — 아키텍처 이식성의 증명

2026-07-23~24, 하루 반 만에 **6개의 콘텐츠 루프**를 관통했다. 대상은 배포 모델이 근본적으로 다른
프로젝트(hot-update / Addressables)다.

| 루프 | 대상 | 결과 |
|---|---|---|
| §9 | **첫 관통** — 샘플룸 위에 RoomCore + Ruler | ✅ Core를 **verbatim 이식**(§2 API 차이 **0**), §5 전 신호 MCP 자동판정 PASS. 5층 구조 정리 + SceneId 보존 실측 |
| §10 | **Chat** | ✅ verbatim 포트, §5 단일 클라 PASS. ⛔ 2인은 인프라 블록(B 프로세스 부재) |
| §11 | **GrabbableProps (XRI 그랩)** | ✅ §5 PASS. **⭐ XRI 3b 경계 규칙 확정** |
| §12 | **TargetProps** (D2 Loop 1) | ✅ §5 PASS. 4과녁 네트워크 스폰, 명중 → 버스 발행 |
| §13 | **ScoreHud** (D2 Loop 2) | ✅ §5 PASS. TargetProps와 **상호참조 0**(grep 양방향), 구독 해지 실증 |
| §14 | **TargetShootoutMatch COMPOSITION** (D2 Loop 3) | ✅ **studio 첫 COMPOSITIONS 층** + **§5 서버권위 루프 실증(주입 아닌 실 흐름)** |

**⭐ 결론: 5층 전체(SYSTEMS / ENVIRONMENT / UI / FEATURES / COMPOSITIONS)가 studio에서 성립.**
6개 콘텐츠 오브젝트 공존, Error 0, FEATURE↔FEATURE 참조 0 유지, **신규 플랫폼 API 0**.

**이 트랙의 기술적 의미.** 계약 코드가 배포 모델이 다른 프로젝트로 **API 차이 0**으로 옮겨갔다는 것은
계약이 특정 프로젝트의 우연에 기대지 않았다는 뜻이다. 이식 과정에서 계약(`Contracts.cs` / `RoomCore`)의
diff는 **IDENTICAL**이었다 — `IEventBus`조차 verbatim 복사로 이미 상속되어 D2 선행 작업을 건너뛸 수 있었다.

**⭐ XRI 3b 경계 규칙 (이후 모든 XRI FEATURE의 SSOT).** studio는 hot-update 경계 때문에 직렬화가 까다롭다.
실측으로 확정한 규칙: **base 어셈블리 컴포넌트(XR Grab Interactable / Rigidbody)는 프리팹에 직접 직렬화해도
되고**(선례 + 실측), **hot 어셈블리 뷰는 직렬 필드 0 + 런타임 배선**으로 간다. 그랩의 성립 방식도 XRCollab의
클릭이 아니라 **XRI `selectEntered` → 소유권 요청**으로 달라졌다.

#### ① 인프라 — ParrelSync + 역할 브리지

**매니페스트 무수정 도입.** GitHub 릴리스 `.unitypackage`를 풀어 GUID를 보존한 채 `Assets/ThirdParty/`로
재배치했다(⛔ UPM git URL 미사용). 결과: 컴파일 0, 메뉴 노출, **`Packages/manifest.json` md5 세션 전후 동일**.

**클론 레이아웃 실측:**

| 경로 | 처리 | 함의 |
|---|---|---|
| `Assets` / `ProjectSettings` / `LocalPackages` | **심링크** | A·B가 씬·설정·소스를 **공유** → "B만 다른 씬"은 불가 |
| `Library` / `Packages` | **복사** | 콜드 재임포트 회피 (≈3 GB, 1회성) |
| `UserSettings` | 클론이 새로 만듦 | **MCP 포트가 갈리는 근거** |

**⭐ 역할 브리지 — 문제와 해법.** 호스트/클라 역할을 정하는 플래그의 **값이 씬 에셋에 살고**, 그 씬은
심링크로 공유된다. 즉 **역할은 런타임에 뒤집는 수밖에 없다.** 해법: `[InitializeOnLoad]`가 클론 여부를
읽어 세션 상태에 기록 → `[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]`가 private 필드를 리플렉션으로
덮는다.

> **⭐ 지시안보다 단순해진 설계.** 원안은 "Editor 훅 → 세션 상태 → **런타임 얇은 컴포넌트**"였으나,
> `[RuntimeInitializeOnLoadMethod]`가 **Editor 어셈블리에서도 발화함을 실측 증명**해서 런타임 컴포넌트를
> 없앴다. 그 결과 하네스가 hot-update 배포물에 섞이지 않고, **shipped 씬을 건드릴 필요도 없어졌다.**
> 타이밍 안전마진도 확보된다 — `AfterSceneLoad`는 모든 `Awake` 후 · 모든 `Start` 전이다.

**fail-closed를 재현으로 증명.** 원본 에디터에서 Play → 마커 `applied=False`(= 훅은 **돌았고** 아무것도
안 함) + 플래그 값 유지 + 아바타 스폰 + **씬 에셋 md5 불변**.

**클론 조종 채널.** B에는 MCP가 없으므로 판정은 `-logFile`, 명령은 루트의 `.promptscene-cmd`(1줄 = 1명령,
소비 후 삭제), 자동 Play는 루트의 `.promptscene-autoplay`. **루트에 두는 것이 핵심** — `Assets/` 안에
두면 심링크로 A까지 무장된다. 역할이 client가 아니면 업데이트 구독조차 하지 않는다(A에서 완전 불활성, 실측).

## 8. 발견한 함정과 대응

이 절은 프로젝트의 **재사용 가능한 기술적 기여**다. 전부 실측이며, 각각 해당 SSOT 문서에 역기입되었다.

### 8.1 ⭐ 스크립트 단발 빌드의 FishNet SceneId 미할당 (2026-07-13)

| | 내용 |
|---|---|
| **증상** | **조용하다.** 룸 입장 · 로비 소멸 · 스포너 복제까지 정상이고 서버 로그에 "become a player"까지 뜨는데 **아바타만 스폰되지 않는다** |
| **원인** | `NewScene → 배치 → SaveScene`을 한 번의 스크립트 실행으로 끝내면 FishNet의 자동 SceneId 생성 훅이 **비결정적으로 건너뛰어져** 스포너가 `SceneId=0 / IsSceneObject=false`로 저장된다 |
| **왜 오진하나** | "become a player" 로그는 상위 세션 레벨이라 FishNet 스폰 실패와 무관하게 뜬다 |
| **해법** | 저장 직전에 `NetworkObject.CreateSceneId(scene, force:true, out changed)` + 각 오브젝트에 `ReserializeEditorSetValues`(둘 다 internal → 리플렉션) 후 `SaveScene`. 빌더 로그의 `sceneIdsGenerated≥1` 확인 |
| **왜 함정인가** | 여러 스크립트 호출에 걸쳐 씬을 열어 두고 저장하는 흐름은 훅이 붙을 틈이 있어 **우연히 통과하기도 한다** |

관련: 씬 네트워크 오브젝트를 재배치하면 SceneId가 바뀌므로 **서버 실행 파일 재빌드**가 필요하다.
studio에서는 별도 경로로 안전 절차를 확립했다 — persistent 오픈 씬 + SaveScene(훅 발화) +
`SceneId!=0 / IsSceneObject` 재확인 + QuickTest, 4단계.

### 8.2 VR 클라의 Main Camera 충돌

룸 씬의 `Main Camera`(데스크톱/에디터 검증용)가 VR 클라에서 유지되는 XR 리그 카메라와 충돌해 **화면
깜빡임 + 시점 고정**을 유발한다("2 audio listeners" 경고 동반). → Main Camera를 **비활성화하고 태그를
Untagged**로 두면 카메라 조회가 XR 리그로 잡힌다.

### 8.3 가드 정규식의 Windows 백슬래시 fail-open

§6.2 참조. **교훈:** 가드는 통과 테스트가 아니라 **차단 재현**으로 검증한다.

### 8.4 플러그인 로딩 지형

- **하위 폴더에서 세션을 열면 플러그인이 로드되지 않아 가드 훅이 아예 발동하지 않는다**(보호가 조용히
  사라짐). 반드시 마켓플레이스 루트에서 시작
- **플러그인 루트에 Unity 프로젝트가 있으면 설치가 EBUSY로 실패**한다(Library 파일 락). → 플러그인을
  하위 폴더로 **분리**해 설치기가 Unity 프로젝트를 건드리지 않게 했다
- **훅/스킬 변경은 재설치 + 세션 재시작**이 필요하다
- **세션 도중 새로 만든 에이전트·스킬은 그 세션에서 등록되지 않는다**(레지스트리는 세션 시작 시 로드)

### 8.5 ⭐ MCP 포트는 고정이 아니라 경로 해시다

MCP 플러그인의 포트는 설정이 없을 때 **SHA256(소문자 CWD) → 20000 + h%10000** 으로 결정된다. 재현 계산과
실측이 일치했다(원본 21017 / 클론 25821). `UserSettings/`가 클론에 복사되지 않으므로 클론은 자기 경로로
새 설정을 굽는다 → **포트 충돌은 구조적으로 불가능**하고 수동 분리가 불필요하다.

### 8.6 ParrelSync 클론 트랩표 (T1~T9, 전부 실측)

| # | 트랩 | 대응 |
|---|---|---|
| T1 | **심링크 씬 공유** — A/B가 역할 플래그를 같이 읽는다 | 역할은 런타임 분기, 클론 전용 상태는 **프로젝트 루트**에 |
| T2 | **MCP 포트 = 경로 해시** | 충돌 구조적 불가 (§8.5) |
| T3 | ⛔ **클론 MCP의 NuGet 재복원이 Play를 끊는다** — 클론 시작 ~6분 뒤 도메인 리로드 → 클론 Play 종료. **첫 재조인 실패의 진짜 원인이었다(넷코드 문제 아님)** | 재복원 후 재Play. 근본 대응 = 클론에서 MCP 비활성 |
| T4 | ⛔ **클론 종료가 원본의 MCP 서버를 죽인다** (에디터 자체는 멀쩡, 자동 재기동 없음) | 서버 바이너리 수동 재기동으로 복구(실측 성공) |
| T5 | **클론 첫 컴파일이 원본의 ILPP 러너 프로세스를 kill** 한다 | Unity가 필요 시 재기동. 이번 세션 영향 없음(관측) |
| T6 | **ParrelSync가 공유 Assets에 자산을 쓴다**(클론 생성 시 원본 쪽에 설정 자산 생성) | 무해하나 인지 필요 |
| T7 | **공유 NuGet DLL — 실제로는 무사**(파일 127개 불변, 당일 수정 0건) | 위험은 T3로 나타나지 DLL 손상으로는 안 나타났다 |
| T8 | **입력 포커스** — 에디터 2개 중 활성창만 실입력을 받는다 | 이번 세션은 실입력을 아예 안 써서 우회. **실 키보드 2인 조작은 미검증** |
| T9 | **디스크·시간** — 클론 ≈3 GB / 1분 미만, 콜드 오픈 ≈5분 | — |

**T3·T4는 오진 방지 관점에서 특히 중요하다.** 둘 다 증상이 네트워크 실패처럼 보이지만 원인은 툴체인이다.

## 9. 만들지 않기로 한 것들 — 설계 규율의 증거

이 절은 **하지 않은 결정**의 기록이다. 정직 계약과 승격 규칙이 실제로 작동했다는 증거이므로 기술
심사 관점에서는 성공 사례만큼 중요하다.

### 9.1 런치패드 UI — 보류·롤백 (2026-07-07~08)

**하려던 것:** 맥북 런치패드식 아이콘 그리드 UI + 토글 기능을 계약 위에 얹고, 궁극적으로 "마피아 게임
만들어줘" 같은 대화형 생성으로 확장.

**실제로 증명된 것(정직하게):** 1인(에디터 클라) + 서버로 조인 · 아바타 스폰 · 로비 소멸 · 런치패드
실제 클릭 · 룰러 측정/지우기 · 설정 창 동작 · 서버권위 미션 상태 동기화(0→3).

**보류 사유:**
1. **멀티플레이가 눈으로 확인 안 됨** — 끝까지 1명 + 서버만 테스트. "다른 사람이 로딩되어 서로 보이는"
   그림이 없었다
2. **게임이 "보이지" 않음** — 미션은 로그로만 확인. 화면에 뜨는 진행도/결과가 없어 "게임"이라 하기 어렵다
3. **미감** — 앱 아이콘식 모노그램 타일 수준. 자동 미감 판정 불가

**조치:** 작업물 전부(스킬·씬·UI 스크립트·계약 추가분·기존 파일의 이번 세션 변경)를 **되돌려 제거**하고,
무엇을 했고 무엇이 증명됐고 무엇이 부족했는지를 회고 문서로 남겼다. 기존 코어·스킬·룸 씬은 건드리지 않았다.

**파급:** 이 회고가 이후 세 가지를 낳았다.
- **"수요 없는 추상화 금지"** — D2 착수 시점을 "서로 통신하는 기능 2개가 실제로 생기는 순간"으로
  못박은 근거
- **"게임 로직 정확성은 구조 하네스로 안 된다"** — N명 플레이테스트 하네스를 프론티어로 등록
- **입력·네트워크 지형 지식 6항목** — 다시 할 때 유효한 실측을 회고에 남겨 이후 세션이 재발견하지
  않도록 했다

대신 실용적 대안을 취했다: 아이콘 그리드가 아닌 **최소 플레이 HUD**(레지스트리 순회 토글 + 클리어,
IMGUI). "이쁘게"가 아니라 "플레이 가능하게"가 목표다.

### 9.2 `INetMessaging` 계약 승격 — 보류 (2026-07-20)

M3 완료로 FEATURE 내부 네트워크 사용이 3건이 된 시점에 승격 여부를 판정하는 검토서를 썼다.
**판정: 보류.**

| 소비자 | 수요의 본질 |
|---|---|
| M1 Ruler | **오브젝트 결합 상태 전파.** late-join 백필이 **필요**(늦게 온 클라도 선을 봐야 함) |
| M2 Grabbable | **소유권 + transform 동기화.** 자기 RPC가 거의 없음 — **메시징이 아예 아님** |
| M3 Chat | **오브젝트 무관 방송 버스.** 백필은 오히려 **유해**(마지막 1건만 남아 "이력처럼 보이는 거짓말") |

**왜 같은 모양이 아닌가:**
1. **전달 의미론이 상충한다.** 하나의 계약으로 덮으면 이 차이가 옵션 플래그로 숨는데, 그 플래그의 올바른
   값은 **기능의 도메인 지식**이다 — 계약이 정책을 삼키는 모양(메커니즘-비정책 위반)
2. Grabbable은 표에 있을 뿐 **소비자가 아니다**
3. **순수 버스 수요는 채팅 1건** — 두 소비자 규칙 미충족. Ruler를 버스 위로 옮기는 건 승격을 정당화하기
   위한 **역방향 리팩터링**이지 수요가 아니다
4. **패턴 복제 비용이 아직 싸다** — 복제 3벌의 유지비 < 계약 1개의 고정비(문서 · 하네스 · 모든 룸의
   호환성 보증)

**재개 트리거를 명시했다:** 두 번째 순수 버스 소비자(리액션/핑/투표/상태 알림)가 실제로 생길 때. 그때도
전달 의미론은 **옵션 플래그가 아니라 계약 분리**로 다룬다.

### 9.3 소유권 계약 승격 — 보류 (2026-07-16)

조사 결과 소유권 코어가 이미 패키지 레이어에 있고 접점은 한 줄이므로, **FEATURE 지역 사용으로 충분**하다고
판정했다. 계약 승격은 **두 번째 잡기-소유권 소비자**가 실제로 생길 때 재검토한다. 설계 문서의 원래
기술("SYSTEMS 소폭 확장 필요")을 **취소선으로 정정**해 기록했다 — 틀린 예측을 지우지 않고 남겼다.

### 9.4 예측(client-side prediction) — 견적 후 보류 (2026-07-21)

읽기 전용 정찰(P-G0)로 견적만 냈다. **판정:**

- 예측은 플랫폼 래퍼를 **통과해 직접 도달 가능**하다(래퍼 런타임에 예측 코드 0건, 뷰가 파이프라인에 무개입)
- 그러나 **NetworkManager에 PredictionManager + 프리팹별 활성 플래그**를 요구해 M-시리즈의 **"SYSTEMS
  무수정"을 깬다**
- → "보류"의 이유가 *불가능*이 아니라 **SYSTEMS 해동 + 검증 인프라 비용**임이 확증되었다
- 낭보 1건: 지연/손실 시뮬레이터가 네트워크 라이브러리에 내장되어 있다(검증 인프라 확보 가능)
- 비용 등급: **도달성 낮음 / 구조 공사 높음**

**정찰의 방법론도 기록해 둘 만하다.** 서브에이전트가 소스에서 근거를 수집하고, 메인이 **하중이 큰 주장만
재검증**했다. 신뢰를 위임하되 결론은 직접 확인하는 분업이다.

### 9.5 ⭐ 개척 금지의 완화 — 3분 등급 도입 (2026-07-27)

초기 능력 지도는 ✅(가능)와 ⛔(불가) 2분이었다. 문제는 **"에셋이 없다 / public setter가 없다 / 아직
아무도 안 해봤다"** 가 전부 ⛔로 분류되어, 코드로 충분히 닿는 일까지 거절하게 된다는 점이었다.

**개정: 3분 등급.**

| 등급 | 정의 | 행동 |
|---|---|---|
| ✅ **재조합** | 라이브 검증된 기계의 조합 | 그대로 짓는다 |
| ⚠ **코드-대체** | 사람의 창작물 없이 · SYSTEMS 수정 없이 **코드로 닿는다** (에디터 스크립트 절차 생성, private 필드 런타임 리플렉션, 없는 컴포넌트의 콘텐츠측 대체 구현) | **짓는다.** 코드-대체물임을 **라벨링**하고 격차는 **추천사항**으로 남긴다 |
| ⛔ **개척** | 게이트 딱 셋: **(a)** 코드가 대신할 수 없는 사람의 미감/창작 판정 **(b)** 플랫폼 오너 결정(승격·SYSTEMS 해동·패키지 변경) **(c)** 없는 인프라 | 의향 기록 + 개척 청구서 |

**등급은 요청 덩어리가 아니라 슬라이스 단위로 매긴다.** 예: "의자에 앉은 아바타"는 ⚠(앉은 *형태*는
절차 생성 코드로 만든다) + ⛔(a)(잘 앉은 *느낌*은 사람이 본다)로 쪼개진다. 실제로 이 개정으로 기존
개척 청구서의 항목 3개가 ⚠로 해소되고 미감 판정만 남았다.

함께 도입한 규율: **⛔(b) 판정 전에는 SYSTEMS를 안 건드리는 콘텐츠측 경로를 먼저 찾아본다.** 그리고
스킬 절차 마지막에 **사람의 UI 테스트 핸드오프를 필수로 제안**한다 — 기계가 못 보는 축을 사람에게 넘긴다.

## 12. 한계와 남은 과제

### 12.1 구조적 한계 (설계상 증명할 수 없는 것)

1. **미감·재미·밸런스.** 하네스는 "게임에 들어갈 자격"은 재도 "이쁜가"는 못 잰다. 사람 또는 비전 루프가
   필요하다.
2. **게임 로직의 정확성.** 구조 하네스로는 안 된다. **시뮬 플레이어 N명 플레이테스트 하네스**가
   프론티어로 남아 있다.
3. **실기기 손맛.** 코드 경로는 시뮬/실기기가 동일함을 소스 검증했으나, 조작감은 실기기 + 사람 판정이다.

### 12.2 미실증 (인프라·범위 문제)

| 항목 | 상태 |
|---|---|
| Grab 핸드오버 · 과녁→점수 studio 파리티 | ⬜ 해당 FEATURE가 현존 룸에 미배치. **`/add-component`로 배치하면 즉시 집행 가능** |
| 실 키보드/마우스 2인 조작 | ⬜ T8 — 이번까지는 프로그램 채널로만 조종해 함정을 우회했다 |
| 3인+ 동시 | ⬜ 1게스트 3/3 성공은 실측, 3인+ 미실측 |
| 배포(Smart Deploy / 번들 업로드) | ⬜ 전 구간 미경험 → 별도 문서 후속 |
| 실기기 XR (손 트래킹 · XREAL · 태블릿/Vision · 시선) | ⬜ V2 |
| 실제 포인터 이벤트 → 레이캐스트 원경로 | ⬜ 현재는 경계 지점 주입 |
| 번들 한글 폰트 | ⬜ 현재는 OS 동적 폰트 = 데스크톱 전용 |
| `compose-room`의 COMPOSITION 편입 | ⬜ 합성 스킬은 아직 FEATURES만 안다 |
| `mode:"extend"` · 파라미터 실전달 · 상호배타 충돌 케이스 | ⬜ 합성 스킬의 잔존 미실증 항목 |

### 12.3 우선순위 제안

1. **`/add-component`로 남은 파리티 2종 집행** — 인프라가 이미 서 있으므로 가장 값싼 완결
2. **클론에서 MCP 비활성화** — T3·T4의 근본 대응
3. **N명 하네스** — 선행 과제는 **조인 인프라 안정화**(현재는 수동 재기동에 의존). 판정 코어는
   3회 재사용된 에폭-로그 골격을 승격하는 것이 자연스럽다
4. **시각화 우선** — 진행도/역할/결과를 로그가 아니라 화면에
5. **D3 생성 에셋 파이프라인** — "외형 질문 3종"이 브리프에 등장하는 순간이 착수 신호

## 13. 결론

### 13.1 무엇이 증명되었나

**아키텍처 주장이 두 개의 서로 다른 배포 모델 프로젝트에서 성립했다.** 계약 코드가 API 차이 0으로
이식되었고, 층을 하나 얹는 동안(`COMPOSITIONS`) 계약 인터페이스는 무변경이었으며, `FEATURE↔FEATURE
참조 0`이라는 구조 불변식이 기계 판정으로 유지되었다. 6개 콘텐츠가 한 룸에 공존하면서도 서로를 모른다.

**자동화의 가치 명제가 실측으로 뒷받침되었다.** 프로젝트가 처음 정한 사거리 — "창의적 20%가 아니라
틀리면 다 죽는 80%를 기계로 보장한다" — 는 SceneId 함정(§8.1) 하나만으로도 정당화된다. 증상이 조용하고,
오진을 유발하며, 사람이 하루를 태우고, 기계는 한 줄(`sceneIdsGenerated≥1`)로 잡는다.

**절차가 재현 가능한 형태로 동결되었다.** 5종의 스킬은 각각 자기가 만든 산출물을 자기가 판정하는
**자기검증**을 통과했고, 손으로 만든 결과물과 **동형**임을 확인했다.

### 13.2 방법론적 기여

기술적 산출물과 별개로, 이 프로젝트는 **에이전트 주도 개발의 규율 세트**를 실증했다.

| 규율 | 실제 효과 |
|---|---|
| **정직 계약** — 증명/시연 구분, "밖" 열거, 신호로 말하기 | 결과를 과대 주장하지 않아 다음 세션이 잘못된 전제 위에서 시작하지 않는다 |
| **승격 게이트** — mechanism-not-policy + rule-of-two | 계약이 god 인터페이스로 자라는 것을 **3회 실제로 막았다** |
| **수요 구동 착수** — "서로 통신하는 기능 2개가 생기는 순간" | 런치패드 실패의 교훈을 재발 방지 규칙으로 전환 |
| **SSOT + 참조 호출** — 절차를 복제하지 않는다 | 절차가 두 곳에 살아 하나가 낡는 사고를 구조적으로 차단 |
| **차단 재현으로 가드 검증** | fail-open 결함 1건을 실제로 발견 |
| **역기입 루프** — 문제를 풀면 그 해법을 SSOT 문서에 패치 | 함정 20여 건이 재사용 가능한 자산으로 축적 |
| **판정 주체 명시** — A는 MCP, B는 로그, 미감은 사람 | "누가 어떻게 판정했나"가 항상 기록에 남는다 |

### 13.3 현재 위치

프로젝트는 **"검증된 토대 + 동결된 조립 절차 + 확보된 2클라 검증 축"** 까지 도달했다. 남은 큰 축은
셋이다: **N명 플레이테스트 하네스**(게임 로직 정확성), **생성 에셋 파이프라인**(외형 질문에 답하기),
**실기기·배포**(V2). 이 셋은 각각 착수 신호를 명시해 두었으므로, 신호가 오면 착수하고 오기 전에는
짓지 않는다 — 그것이 이 프로젝트가 지금까지 지켜 온 규율이다.

## 부록 C. 재현 절차 요약

### C.1 플러그인 로드

```
# A. 마켓플레이스 경유 (지속)
/plugin marketplace add oxr-sdk/Promptscene-harness
/plugin install promptscene@promptscene-harness

# B. 로컬 체크아웃 (이 세션만 — 스킬을 편집할 때)
claude --plugin-dir .
```

⚠ **세션은 반드시 마켓플레이스 루트에서 시작한다.** 하위 폴더에서 열면 가드 훅이 조용히 무력화된다.
훅/스킬 변경은 **재설치 + 세션 재시작**이 필요하다.

### C.2 표준 작업 흐름

```
1) 대상 Unity 에디터를 띄우고 MCP 서버가 살아 있는지 확인
2) /promptscene:assemble-room MyRoom          # 5층 골격 + §6.5 자동판정
3) /promptscene:add-component 룰러 on MyRoom  # 컴포넌트 + §5/§6.5 자동판정
     └ 옵션 게이트: UI 검증? / 멀티 검증?      # 선행 선언이 있으면 묻지 않음
4) (옵션) /promptscene:cross-platform-ui Cross on MyRoom
5) (옵션) /promptscene:multiplayer-check Chat on MyRoom
6) 사람 핸드오프 — 룸을 Play 상태로 남기고 조작 레시피 제시
```

### C.3 2클라 검증 (요약)

**1회 준비:** ParrelSync를 `.unitypackage` 재배치로 도입(⛔ UPM git URL 금지) → 클론 생성(≈3 GB) →
역할 브리지 + 클론 하네스 배치(**프로젝트 루트**에 상태·명령 파일).

**매 세션:** A 에디터 Play(host) → 클론 자동 Play(client) → GATE 1 4신호 → GATE 2 컴포넌트 파리티 →
원상복구(씬 md5 대조, 플레이모드 해제, 클론 종료).

**⚠ 반드시 아는 것:** 클론 첫 시작 후 약 6분간 툴체인 재복원으로 Play가 끊길 수 있다(넷코드 문제가
아니다). 클론을 종료하면 원본의 MCP 서버가 같이 죽으므로 수동 재기동이 필요하다.
